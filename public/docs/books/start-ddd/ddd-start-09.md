## 바운디드 컨텍스트

- 하위 도메인마다 같은 용어라도 의미가 다르고 같은 대상이라도 지칭하는 용어가 다를 수 있음
- 즉, 하위 도메인마다 모델을 만들어야 하며 각 모델은 명시적으로 구분되는 경계를 가져야 함
- 모델은 특정한 컨텍스트(문맥) 하에서 완전한 의미를 가짐
- 같은 제품이라도 카탈로그 컨텍스트와 재고 컨텍스트에서 의미가 서로 다름
- 이렇게 구분되는 경계를 갖는 컨텍스트를 **바운디드 컨텍스트(Bounded Context)** 라고 부름

### 특징

- 바운디드 컨텍스트는 모델의 경계를 결정
- 바운디드 컨텍스트는 각자 구현하는 하위 도메인에 맞는 모델을 가짐
- 바운디드 컨텍스트는 도메인 기능을 제공하는 데 필요한 모든 요소를 포함
  - 표현 영역
  - 응용 서비스
  - 도메인 모델
  - 인프라스트럭처
- 하나의 바운디드 컨텍스트는 하나의 하위 도메인에 대응하는 것이 일반적이지만 반드시 1:1인 것은 아님
  - 하나의 하위 도메리를 여러 바운디드 컨텍스트로 나눌 수도 있음
  - 여러 하위 도메인을 하나의 바운디드 컨텍스트에서 처리할 수도 있음

## 바운디드 컨텍스트 간 관계

바운디드 컨텍스트는 서로 협력해야 하므로 다양한 방식으로 관계를 맺는다.

### 공개 호스트 서비스 (Open Host Service)

- 한쪽에서 API를 제공하고 다른 쪽에서 이를 호출하는 방식
- API를 제공하는 쪽은 자신의 모델이 그대로 노출되지 않도록 보호해야 함
- 외부에서 사용할 수 있는 안정적인 인터페이스를 제공
- 내부 모델이 변경되어도 API 계약은 최대한 유지

### 공유 커널 (Shared Kernel)

- 두 바운디드 컨텍스트가 일부 모델을 함께 사용하는 방식
- 중복 구현을 줄일 수 있음
- 공유 모델을 변경하면 양쪽 모두 영향을 받으므로 긴밀한 협력이 필요
- 공유 범위는 최소화하는 것이 좋음

### 고객-공급자 (Customer-Supplier)

- 공급자(Supplier)가 서비스를 제공하고 고객(Customer)이 이를 사용하는 관계
- 고객의 요구사항을 공급자가 어느 정도 반영하며 함께 발전시킴

### 독립 방식

- 서로 직접 의존하지 않고 각자의 모델을 유지
- 이벤트, 메시지 등을 이용해 느슨하게 협력하기도 함

## 바운디드 컨텍스트 구현

### 하나의 바운디드 컨텍스트 = 하나의 패키지?

- 반드시 그렇지는 않음
- 규모가 작다면 하나의 프로젝트 안에서 패키지로 분리할 수 있음
- 규모가 커지면 별도의 프로젝트나 서비스(MSA)로 분리할 수도 있음
- 중요한 것은 물리적인 분리가 아니라 **모델의 경계가 명확한 것**

### 여러 바운디드 컨텍스트 통합

- 다른 컨텍스트의 모델을 그대로 사용하지 않는 것이 좋음
- `ACL(Anti-Corruption Layer)`을 두어 외부 모델을 내부 모델로 변환하면
  - 내부 모델이 외부 모델에 오염되지 않음
  - 외부 시스템 변경의 영향을 줄일 수 있음

## 정리

- 바운디드 컨텍스트는 도메인 모델의 경계를 의미한다.
- 같은 용어라도 컨텍스트가 다르면 의미가 달라질 수 있다.
- 각 컨텍스트는 자신의 모델과 규칙을 독립적으로 유지한다.
- 컨텍스트 간 협력은 API, 이벤트, 공유 커널, ACL 등 다양한 방식으로 이루어진다.
- 중요한 것은 코드보다 **모델의 경계를 명확하게 유지하는 것**이다.
