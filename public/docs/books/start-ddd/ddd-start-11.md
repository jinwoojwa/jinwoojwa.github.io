## 단일 모델의 단점

객체 지향으로 도메인 모델을 구현할 때 주로 사용하는 ORM 기법은 **도메인 상태 변경 기능 구현에는 적합**함.

하지만 주문 상세 조회 화면처럼 여러 애그리거트의 데이터를 조합해서 조회해야 하는 경우에는 고려할 사항이 많아짐.

예를 들어,

- 여러 애그리거트를 조인해야 함
- 지연 로딩(Lazy Loading) 문제를 고려해야 함
- 조회 성능을 위해 DTO를 별도로 구성해야 함

즉,

- 상태 변경에 적합한 모델
- 조회에 적합한 모델

이 서로 다르기 때문에 하나의 모델만으로 구현하면 모델이 복잡해짐.

이를 해결하기 위해 `CQRS(Command Query Responsibility Segregation)` 패턴을 사용함.

---

## CQRS

CQRS는 **명령(Command)과 조회(Query)의 책임을 분리하는 패턴**임.

시스템이 제공하는 기능은 크게 두 가지로 나눌 수 있음.

- 상태를 변경하는 기능(Command)
- 상태를 조회하는 기능(Query)

### Command

상태 변경 기능은

- 생성(Create)
- 수정(Update)
- 삭제(Delete)

와 같이 주로 **하나의 애그리거트의 상태를 변경**하는 작업임.

도메인 모델과 비즈니스 규칙이 중요함.

### Query

조회 기능은

- 여러 애그리거트의 데이터를 함께 조회하는 경우가 많음.
- 화면에 필요한 형태로 데이터를 조회하는 것이 중요함.
- 복잡한 JOIN이나 조회 전용 DTO를 사용하는 경우가 많음.

즉,

- 상태 변경 범위와
- 조회 범위가

정확하게 일치하지 않음.

따라서 하나의 모델로 두 기능을 모두 처리하면 모델이 불필요하게 복잡해짐.

---

## CQRS 구조

```text
                Command
사용자 ───────────────▶ Command Model
                           │
                           ▼
                        Database
                           ▲
                           │
사용자 ◀────────────── Query Model
                 Query
```

- Command Model은 상태 변경만 담당함.
- Query Model은 조회만 담당함.
- 두 모델은 서로 다른 방식으로 구현될 수 있음.

---

## CQRS의 장점

### 모델이 단순해짐

- 명령 모델은 비즈니스 규칙에 집중할 수 있음.
- 조회 모델은 조회 성능에 집중할 수 있음.
- 각 모델의 책임이 명확해짐.

### 구현 기술을 다르게 사용할 수 있음

각 모델에 적합한 기술을 선택할 수 있음.

예를 들어

- Command Model → JPA
- Query Model → MyBatis

처럼 구현 가능함.

조회 모델은 SQL을 직접 작성하는 것이 더 효율적인 경우가 많음.

### 서로 다른 저장소를 사용할 수 있음

명령 모델과 조회 모델이 서로 다른 저장소를 사용할 수도 있음.

예를 들어

- Command Model → MySQL
- Query Model → Redis
- Query Model → Elasticsearch
- Query Model → MongoDB

처럼 구성 가능함.

조회 모델은 조회 성능이 좋은 저장소를 자유롭게 선택할 수 있음.

### 조회 성능 향상

조회 모델은 화면에 필요한 형태로 데이터를 미리 만들어 둘 수 있음.

따라서

- JOIN을 줄일 수 있음.
- 복잡한 조회를 단순화할 수 있음.
- 조회 속도를 향상시킬 수 있음.

---

## CQRS의 단점

- 명령 모델과 조회 모델을 각각 구현해야 하므로 구조가 복잡해짐.
- 조회 모델을 별도로 유지해야 함.
- 조회 모델을 동기화하기 위한 이벤트 처리가 필요할 수 있음.
- 명령 모델과 조회 모델 간에 일시적인 데이터 불일치(Eventual Consistency)가 발생할 수 있음.

---

## 언제 사용하는가?

다음과 같은 경우 CQRS를 고려할 수 있음.

- 조회 기능이 매우 복잡한 경우
- 조회 성능이 중요한 경우
- 조회와 변경의 요구사항이 크게 다른 경우
- 대규모 서비스에서 읽기와 쓰기를 분리해야 하는 경우

반대로

- CRUD 위주의 단순한 서비스
- 규모가 작은 프로젝트

에서는 CQRS를 적용하지 않는 것이 더 단순하고 유지보수하기 쉬울 수 있음.

---

## 정리

- CQRS는 명령(Command)과 조회(Query)의 책임을 분리하는 패턴임.
- 상태 변경 모델과 조회 모델을 분리하여 각각의 목적에 맞게 설계함.
- 명령 모델은 비즈니스 규칙에 집중하고, 조회 모델은 조회 성능에 집중함.
- 명령 모델과 조회 모델은 서로 다른 구현 기술이나 저장소를 사용할 수 있음.
- 복잡한 조회와 높은 조회 성능이 필요한 시스템에서 특히 효과적임.
- 단순한 시스템에서는 오히려 복잡도가 증가할 수 있으므로 필요한 경우에만 적용하는 것이 좋음.
