## 시스템 간 강결합 문제

예를 들어 주문 취소 시 다음과 같은 작업이 필요하다고 가정하면,

- 주문 상태 변경
- 결제 취소
- 포인트 복원
- 쿠폰 복원
- 알림 발송

이를 모두 `OrderService`에서 직접 호출하면 다음과 같은 문제가 발생함.

- 여러 바운디드 컨텍스트에 직접 의존하게 됨
- 새로운 후처리가 추가될 때마다 기존 코드를 수정해야 함
- 하나의 서비스 장애가 다른 서비스까지 영향을 줄 수 있음
- 변경에 취약한 구조가 됨

이러한 컨텍스트 간의 결합을 줄이는 대표적인 방법이 **이벤트(Event)** 임.

---

## 이벤트

이벤트는 **도메인에서 의미 있는 상태 변경이 발생했음을 나타내는 객체**임.

주로 다음과 같은 요구사항을 구현할 때 사용함.

> "~하면 ~를 수행한다."

예)

- 주문이 완료되면 포인트를 적립한다.
- 회원이 가입하면 환영 메일을 보낸다.
- 배송지가 변경되면 배송 시스템에 반영한다.

```text
            이벤트             이벤트
이벤트 생성 주체 --> 이벤트 디스패처 --> 이벤트 핸들러
                    (이벤트 퍼블리셔)
```

### 구성 요소

- 이벤트 생성 주체(Event Publisher)
- 이벤트(Event)
- 이벤트 디스패처(Event Dispatcher)
- 이벤트 핸들러(Event Handler)

이벤트 생성과 처리는 **동기 또는 비동기**로 실행할 수 있음.

```java
public record OrderConfirmedEvent(
    Long orderId,
    Long storeId,
    List<ItemSnapshot> items
) {}
```

- 이벤트 이름은 **과거 시제**를 사용하는 것이 일반적임.
  - `OrderCanceledEvent`
  - `OrderConfirmedEvent`
  - `MemberRegisteredEvent`

### 이벤트 구성

이벤트는 보통 다음 정보를 포함함.

- 이벤트 종류
- 이벤트 발생 시간
- 이벤트를 식별할 수 있는 데이터
- 이벤트와 관련된 추가 데이터

이벤트에는 **최소한의 데이터만 담는 것이 좋음.**

- 필요한 식별자(ID)만 전달
- 필요한 경우에만 조회해서 사용
- 불필요하게 큰 객체를 담지 않음

## 이벤트의 용도

### 후처리(Trigger)

도메인의 상태가 변경되었을 때 후처리가 필요한 경우 사용함.

```text
Order
   │
OrderCanceledEvent
   │
EventDispatcher
   │
OrderCanceledEventHandler
   │
RefundService
```

예)

- 주문 완료 → 포인트 적립
- 주문 취소 → 결제 취소
- 회원 가입 → 환영 메일 발송

### 시스템 간 데이터 동기화

서로 다른 시스템이 동일한 데이터를 관리하는 경우 이벤트를 이용해 동기화할 수 있음.

예)

```text
배송지 변경
      │
AddressChangedEvent
      │
배송 시스템
```

회원 서비스는 배송 시스템을 몰라도 됨.

---

## 이벤트의 장점

### 도메인 로직 분리

이벤트를 발생시키는 쪽은

> "이벤트를 발생시켰다."

까지만 책임짐.

후처리는 각각의 핸들러가 담당함.

즉,

- 주문은 주문만 책임함.
- 결제는 결제만 책임함.
- 알림은 알림만 책임함.

### 기능 확장이 쉬움

예를 들어

```text
주문 완료
```

후

- 포인트 적립
- 알림 발송
- 통계 저장

을 수행하다가

```text
추천 시스템 갱신
```

이 추가되어도 새로운 핸들러 하나만 추가하면 됨.

기존 코드를 수정할 필요가 거의 없음.

## 동기 이벤트 처리 문제

동기 방식에서는 이벤트를 발행한 스레드가 핸들러의 작업이 끝날 때까지 기다림.

### 장점

- 구현이 단순함.
- 하나의 트랜잭션으로 처리하기 쉬움.

### 단점

- 후처리가 오래 걸리면 원래 기능도 함께 느려짐.
- 핸들러가 실패하면 원래 기능도 실패함.
- 서로 강하게 연결됨.

예)

```text
주문 완료
   │
결제
   │
메일 발송(5초)
   │
사용자는 주문 완료까지 5초 대기
```

## 비동기 이벤트 처리

이벤트를 별도의 스레드나 메시징 시스템에서 처리하는 방식임.

### 장점

- 원래 기능이 빠르게 종료됨.
- 시스템 간 결합이 줄어듦.
- 장애 전파를 줄일 수 있음.

### 단점

- 구현이 복잡함.
- 데이터가 즉시 반영되지 않을 수 있음. (Eventual Consistency)

### 메시징 시스템 이용

대표적으로

- Kafka
- RabbitMQ
- AWS SQS

등을 이용함.

```text
Order
   │
Event
   │
Message Broker
   │
Consumer
```

여러 시스템이 동일한 이벤트를 구독할 수도 있음.

### 이벤트 저장소 이용

이벤트를 DB에 저장한 뒤 별도의 프로세스가 주기적으로 읽어서 처리하는 방식임.

```text
Order
   │
Event Table
   │
Event Processor
   │
Handler
```

메시지 브로커가 없어도 구현 가능함.

---

## 이벤트 처리와 DB 트랜잭션

가장 중요한 것은

> **DB 변경과 이벤트 발생의 일관성을 보장하는 것**임.

잘못 구현하면

```text
주문 저장 성공

↓

이벤트 발행 실패
```

또는

```text
이벤트 발행 성공

↓

DB 롤백
```

같은 문제가 발생할 수 있음.

이를 방지하기 위해 보통 다음 방법을 사용함.

- 트랜잭션이 성공적으로 커밋된 후 이벤트를 발행함.
- `@TransactionalEventListener`의 `AFTER_COMMIT` 옵션을 사용함.
- Outbox Pattern을 사용하여 DB와 이벤트 발행의 일관성을 보장함.

---

## 정리

- 이벤트는 도메인에서 발생한 중요한 사실을 표현함.
- 이벤트를 사용하면 바운디드 컨텍스트 간 결합을 줄일 수 있음.
- 후처리와 시스템 간 데이터 동기화에 많이 사용됨.
- 동기 방식은 단순하지만 성능과 장애 전파 문제가 있음.
- 비동기 방식은 확장성이 좋지만 구현이 복잡하고 최종 일관성을 고려해야 함.
- 이벤트는 **트랜잭션과의 일관성**을 반드시 고려하여 발행해야 함.
